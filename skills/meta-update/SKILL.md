# meta-update

セッション中の学びを永続化するskill。CLAUDE.mdの「自己改善」シグナル検知時に起動される、または手動起動。引き金の判定はCLAUDE.md側、抽出・ルーティング・承認・書込はこのskillの責務。

## 原則

- **提案のみ**: 勝手に書かない。記録先と内容を提示し承認を得てから反映
- **コード・命名は変更しない**: 誤誘導の原因がコード構造/関数名/コメントの場合、改善は提案テキストに留める(プロダクト資産のため)
- **遅延コミット**: 投機的に記録しない。実需(再発・明示要求)が確認できた学びのみ
- **記録より仕組み**: 学びごとに、まず「失敗を起こらなくする/自動で検出する仕組み」(スクリプト・CI・テスト・lint・設定の自動導出・hook)を検討し、文書の記録先と並べて提示する。仕組みで防げるなら、文書の記録は不要か補助に留める。仕組みの実装はプロダクトの変更なので、提案として出し、承認後に通常の作業として行う
- **global CLAUDE.md は最後の手段**: `~/.claude/CLAUDE.md` は全会話に常時載る(1 行でも全セッションのコスト)。記録先は hook → docs → skill → project CLAUDE.md の順に検討し、それで足りない時だけ。候補に出すときは常時コストを明記し、推奨にしない
- **公開先に個人の具体を書かない**: 記録先が公開 repo(`gh repo view --json visibility` で確認)なら、個人を特定・推測できる具体を書かない。具体 = 実名・学校・勤務先・応募先・非公開の repo/project 名・個人の活動・ユーザー名入りのパス。実例も具体になるので、対象を伏せて一般化する(固有名・分野を書かない)。具体が要るなら非公開の置き場所に分け、公開側からは参照しない

## Phase 0: 起動経路の判定

ユーザから起動を促された (= 自発提案でない) 場合、Phase 1 の前に必ず実施:

1. **検知失敗の言語化**: 該当シグナルが本来どの時点で検知できたか / 何故できなかったかを 1-2 文で記述
2. **真因の分類**:
   - シグナル定義の隙間 → CLAUDE.md 自己改善節を Phase 1 学び候補に追加
   - 運用タイミングの問題 → 振り返りチェック項目を追加
   - 判定基準の曖昧さ → 判定フローを具体化
3. 検知ルール更新を本来の学び候補と並べて Phase 1 へ持ち越し

meta-update の提案そのものへのユーザーの訂正(置き場所・方式への指摘)も行動指針シグナル。出し直しで終えず、その回の提案に規範の更新候補として含める。

## Phase 1: 抽出と除外

会話を走査し、永続化すべき学びを1行知識(暗黙知を明文化)に圧縮する。各学びにシグナル(再作業/誤誘導/行動指針/陳腐化)を対応づける。陳腐化は新規追記でなく**既存記述の修正・置換**が成果物(矛盾する注記の追記でなく古い記述自体を直す)。

次を**順に**判定し、1つでも該当すれば除外する:

1. 一回性の事実・特定対象固有の解釈・その場限りの訂正 → 除外(一般則化できない)
2. 別agentテスト: 「同じ情報で別agentも同じ判断/誤解をするか」が NO → 自分固有のミスなので除外
3. 既知の自明則(「READMEを読む」等) → 新規の学びを生まないので除外

残った学びの記録対象範囲を判定する: 当該skillの内部手順としてのみ必要な知識はそのskill内に留める。一方、**meta-update を起動しない通常作業でも遭遇する事象**は「全作業横断知識」として永続化対象とする。docs化の前に既存記載と重複しないか必ず確認する(skill内蔵知識との二重化を避ける)。

## Phase 2: ルーティング判定

### Step 0: 仕組み化の検討(記録先より先に)

学びごとに次を問い、答えがあれば Phase 3 の選択肢の先頭に「仕組み」として出す:

- その失敗を、起こらない形にできるか(例: 手で保つ一覧 → 設定から自動導出、手順 → スクリプト化)
- 起きたら自動で止まる/検出される形にできるか(例: CI・テスト・lint のルール、push 前の検証スクリプト、hook で該当操作を止める)
- 仕組みのコスト(実行時間・利用枠・保守)と、文書の記録で済ませる場合の再発リスクを並べる

仕組みが成り立たないときだけ、Step 1 以降の記録先の判定に進む。

### Step 1: スコープ判定(置き場所を決める)

「他プロジェクトでも成り立つ知識か」で判定:

- YES(環境横断) → `~/.claude` 配下(下表へ)
- NO(特定プロジェクト固有) → 対象プロジェクトの root / そのプロジェクトの `CLAUDE.md`。**先に対象パスを特定**(cwd と対象プロジェクトが異なる場合に注意)

### Step 2: 性質判定(環境横断知識の記録先)

| 学びの性質 | 記録先 |
|---|---|
| 手順・ハマりどころ・ツール仕様・調査結果 | docs |
| 繰り返す定型作業フロー | skill(新規作成 or 既存skill更新) |
| 既存の規則・docs があるのに読まれず効かなかった(見落とし・忘れ) | hook(該当操作の直前に PreToolUse 等で文脈へ注入。常時の文脈コストなし)。docs・CLAUDE.md への追記で済ませない |
| 全体方針・判断基準・参照先の追加 | CLAUDE.md(原則「global CLAUDE.md は最後の手段」の条件のときだけ) |
| コード構造・命名・コメントの誤誘導 | **提案のみ**(書込まず改善案を提示) |

### Step 3: ファイル特定(docs/skill 行きの場合)

カテゴリ決定後、ファイル粒度まで降ろす: 既存 docs/skill を Glob → トピック一致を Grep → 一致あれば**追記**、なければ新規作成。重複記載を避ける。

判断に迷う場合は AskUserQuestion で記録先を確認。

## Phase 3: 承認

記録先・追記内容(diff相当)を提示し、AskUserQuestion で承認を取る。複数の学びがあれば個別に可否を選べる形にする。

仕組みの案は「hook を足す」「スクリプトを作る」で止めず、何を作るかまで書く(ユーザーが中身で判断できるように):

- hook: 種類(PreToolUse・PostToolUse・Stop 等)、対象(ツールと、入力のどの項目をどう照合するか)、動き(止める / 文脈に差し込むだけ)、差し込む・返す文の要点、書き先、常時のコスト(git やファイルを見るなら毎回の費用)。書き先は yhooky の規則のファイル(全環境: `~/.claude/hooks/rules/common.toml`、project 固有: `<project>/.claude/hooks/rules/*.toml`)。正規表現で書けない判定だけ yhooky の組み込みの判定にする(Rust の変更と release が要る)。詳細 `~/.claude/docs/hooks.md`
- スクリプト・CI・test: 名前、いつ・誰が動かすか、何を確かめて何を返すか

### Step 1 のスコープ判定が確定していない場合の選択肢ルール

Step 1(環境横断 vs プロジェクト固有)を独断で決めつけず、**両スコープを選択肢に並べる**。`/copy` のようなユーザー固有の運用や、特定プロジェクトでしか発生しない作業に関する学びは、見た目は一般則でも置き場所はプロジェクト側が妥当になることがあるため、ユーザーに選ばせる。

選択肢テンプレ(仕組みの案があれば先頭に足す):

A. 仕組み: Step 0 の案(何を作るか・コスト)
B. 環境横断: `~/.claude/docs/<topic>.md`・hook・skill に追記(`~/.claude/CLAUDE.md` は原則「global CLAUDE.md は最後の手段」の条件のときだけ)
C. プロジェクト固有: 対象プロジェクトの `CLAUDE.md`(`<cwd>/CLAUDE.md` など)に追記
D. 文言を調整して追記(具体案をユーザーから受ける)
E. 記録しない

「環境横断 = ~/.claude 配下4択のみ」「プロジェクト固有 = 1択のみ」のように片方だけを出さない(記録先のスコープはユーザーが選ぶ)。

判断材料(どちらに置くべきかの目安):

- 「他プロジェクトでも遭遇する作業」(commit手順・PowerShellの罠等) → 環境横断
- 「特定リポジトリ・特定運用に依存する規範」(個人用 repo 固有の運用・特定ツール連携の出力形式等) → プロジェクト固有
- 不明 → 両方を選択肢に出してユーザー決定

## Phase 4: 書込

承認された学びのみ反映:

- docs: 高密度日本語フォーマット(skill `doc-optimizer` 準拠 — カタカナ→英語キーワード、述語省略、箇条書き)
- CLAUDE.mdへの追記は編集ルール遵守(簡潔・箇条書き・長文禁止)
- 公開 repo へ書く前に「公開先に個人の具体を書かない」を確認
- 既存docsに該当があれば新規作成せず追記

## 書込先のsymlink注意(重要)

`~/.claude` 配下はsymlinkでWrite拒否される。書込前に `readlink -f <対象>` で実体パス(dotfiles配下)を解決してからEdit/Writeする。実体マッピングは `~/.claude/docs/symlinks.md` 参照。

## Phase 5: 構造点検

docs を新規作成したら、CLAUDE.md「参照ドキュメント」節か `~/.claude/docs/INDEX.md`(補助 docs index)のどちらかに載っているか確認し、なければ INDEX.md への 1 行追記を提案する。どちらにも載らない docs は grep でしか見つからない。
