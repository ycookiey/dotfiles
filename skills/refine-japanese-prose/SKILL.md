# refine-japanese-prose

日本語文書を平易化する。「書く時」と「書いた後」の両方で使える。適宜更新する前提。

## 使うとき

- 既存の日本語文書(レポート/ブログ/技術文書/メール/プレゼンスライド)を推敲する
- AI生成テキストの臭いを消したい
- 学術過剰な漢語・カタカナを平易化したい
- 馴染みの薄い表現を読みやすくしたい
- スライド+原稿(presenter notes)のセット推敲
- **プレーンテキスト出力時**にもチェック(観点(11) 参照)
  - Markdown/HTML/LaTeX ソース内は組版エンジンに任せる

## 修正観点 (11カテゴリ)

### (1) 馴染みの薄い学術・批評理論用語
- 哲学/批評理論: 還元, 内省, 表象, 相対化, 立脚, 投影, 趣向, 契機, 主観, 客観, 被造物
- 物語論: 構図, 構造, 動員, フレーミング, 影響史, 系譜, 投射, 前面に出る
- 文語的副詞句: 〜のさなか, 〜下で, 後景に退く, 立ち上がる, うかがえる, 根ざす, 反復する, 〜であった
- 硬い熟語: 中心性, 価値中立, リード, 慣行, 留保, プール, 集約, 転機, 版を経て
- 「~性」を含む抽象名詞: 信頼性, 妥当性, 有用性 → 動詞句や問いの形に展開
- 硬い名詞「~主体」「~者」: 報告主体, 活用者 → 動詞化「報告するのは」「活用するのは」
- 「貢献」名詞: 動詞「貢献する」または別表現「価値は~する点にある」「役割は~」

### (2) 不用意な漢字連続
- 5字以上の漢字連続(固有名詞・引用を除く)
- 「普通名詞句 + 固有名」の連結 (例: 「日本人少年正太」 → 「日本人の少年、正太」)
- 造語的複合語 (例: 「人造人間表象」「内面情報」「思考読み取り装置」)
- 3字熟語のうち馴染みの薄いもの (被造物 等)
- 熟語連続の解体: 「盲検化困難」→「盲検化が難しい」、「被験者確保困難」→「被験者を集めにくい」、「専門スキル要求」→「専門スキルが必要」
- 名詞連続には助詞を補う: 「大部分同じ」→「大部分は同じだが」
- 入れ子的な熟語は別表現: 「RCT におけるランダム化」→「RCT 運用時に行う様々なランダム化」

### (3) カタカナ語のAI臭
- 学術カタカナ語: バリエーション, フレーミング, ヤマ場, シナリオ, ラスト, クライマックス(用途次第)
- 固有名詞・専門用語(LAWS等)は除外
- 専門カタカナの日本語化: プロトコル→研究計画, パラダイム→考え方/アプローチ, ゴールドスタンダード→最も信頼される試験形式, アウトカム→成果(何の成果かを明示), オリジナル→元の
- 造語的略訳を避ける: 「電子検索」→「電子的な手段による検索」、「拡張」→「加筆して出す」など具体動作、「概念ツール」→「設計や記法のツール」

### (4) AI生成の典型構文
- 自己言及: 「本稿は〜論じる」「本論で扱う」「以下、〜する」
- 形式的命名宣言: 「便宜的に〜と呼ぶ」「〜と位置付ける」「(以下〜)」
- 中庸結語: 「〜うる」「〜だろう」「〜とも言える」「〜と読める」「〜と読み直せる」「〜ことが多い」「〜とは限らない」「価値あり」「~として有力」
- 二項対比反復: 「Aではなく Bである」「普遍主義 vs ナショナリズム」
- メタファー結語: 鏡, 触媒, 縮図, 逆照射, 手掛かり, 材料
- 律儀すぎる補足: 初出全員フルネーム+著作カッコ, 英語フルスペル併記
- 疑問文→自答の構造(ドラマチック): NG「なぜ○○のか。本書は△△としています。」OK 淡々と理由を述べる
- プレゼン口調の聴衆投げかけ: 「~と思われるかもしれません」は学術発表で過剰
- 二重表現の冗長修飾: 「直接引用」→「引用」、「フルタイトル」→「タイトル」
- 評価的意訳の禁止: 引用元 `quoted as saying` を「名言」と訳すと過剰。中立的に「発言」
- 「~と。」のような体言止め未満の終わり: →「~ということです」のような完結形に
- 「~させられる」の曖昧表現(受身か可能か不明): 能動の可能形なら「~することができる」と明示

### (5) 内輪言及
- 「課題が言う」「本稿は」「先生が」など、その場限りの文脈に閉じた言及
- 出典は文末括弧で抽象化 or 受動形で文意保持
- 次節・他章への視覚的ナビゲーション: 「（次節）」「N 部で扱う予定」だけでは読者が迷う → 分担を対比構造で明示
- 書誌的説明: 「枠囲みで」「脚注で」など参照物の物理体裁は読者に不要

### (6) ダッシュ「――」と中黒「・」と機種依存記号
- ダッシュは「である」「すなわち」「(...)」に置換
- 列挙の中黒は読点「、」に置換
- 固有名(カレル・チャペック等)の中黒は維持
- 機種依存記号 `=` `+` `×` を本文ラベルに使わない: 「ラベル = 説明」→「ラベルは説明」、「A + B」→「A と B」、「A × B」→「A、B を組み合わせる」
- 矢印 `→` でレイアウト誘導しない (`(図1.1 →)` のような視覚誘導)
- subtitle の数字括弧 `(1) (2) (3)` は許容 (視覚補助のみ)。ただし口頭(原稿)では「2 点目の」「3 つ目の」と展開

### (7) 事実 vs 解釈 (引用元と書き手の解釈を区別)
原典(本書/論文/サーベイ/参考文献)に基づく文書全般に適用。

- **基本事実と解釈の区別**: 引用元記載 + 一般辞書定義 = 直接掲載 OK。書き手独自の解釈 = 「これは解釈」と明示、または本文外(注・口頭補足)
- **原典で曖昧な語は限界を明示**: 「原典には明示されていませんが、私は ○○ と解釈しました」。「一般には ○○」より「私は ○○ と解釈しました」のほうが誠実
- **原典が示しているだけでは「なぜ?」と問われる**: 理由を解釈で補足
- **既存の例示と被る「私の理解」は無意味**: 新しい視点を加えるか、入れない
- **原典外情報は断定を避ける**: 「~です」より「~だと理解しています」「~だと考えられます」「~の一つでしょう」
  - ※注: 観点(4) の中庸結語回避と逆向き。**書き手の主張は断定が望ましいが、原典外情報や解釈は中庸表現で限界明示**。文脈で使い分け
- **原典外説明から原典記載に戻るときは合図**: 「原典の内容に戻ります」など
- **原典の前置きやニュアンス語から自分の言葉で言い換えない**: 修飾語を反映したつもりでも、原典にない断定(「~の問題だ」)は解釈
- **本文外の補足は明示的にラベル付け**: 「以下、原典にない補足:」のような sub-bullet 階層

### (8) 口頭発表・原稿(presenter notes)
スライド・スピーチ用ノート全般。

- **発音不可記号は文章化**: `→` `(2)` `・` などは口頭で読めないため言葉に展開
- **音読 vs 視覚補助の使い分け**:
  - スライドで視覚的に出ている URL・英語語句は原稿で読み上げない
  - スライドに併記された引用句の和訳は原稿でも読み上げる(音声で理解)
- **常体・敬体の混在を避ける**: 原稿全体を敬体(です・ます)で統一
- **体言止めの多用を避ける**: 「○○な立場。」→「○○な立場です」
- **過去形の発表口調**: 「明示はありません」→「明示されていませんでした」
- **指示語の明確化**: 「ここでの『独立した』」のように補足対象を具体化。補足までの距離が長い場合はさらに具体化
- **主体が曖昧な語を避ける**: 「出現」→「どう生まれたか」、「データの選び方」→「レビュアーによるデータの選び方」
- **論理関係(順接 vs 並列)を正確に**: 原典が並列で挙げた事実を「~ため、~」と順接にしない
- **書き手の戸惑いを読者と共有する**: 「私は分からなかったのですが、自分なりに以下のように解釈しました」
- **次セクションへの繋ぎは短く 1 文で**
- **英語人名はカタカナ + 「ら」で簡略化**: 「Booth, Papaioannou, Sutton」→「ブースら」
- **英語表記の括弧併記は原稿に入れない**: スライドの視覚補助はそのまま、原稿では日本語のみで通す
- **「点」が短い文に 2 回現れる重複を回避**: 「○点目は、〜という点です」→「〜ことです」
- **同一語の繰り返しを後半で言い換え**: 「結論を導けるか」直後の「結論できるか」→「言えるか」
- **略語のフル展開**: 「SR」→「システマティック・レビュー」のように口頭ではフル展開
- **対応する本文記述がない部分を原稿に入れない**: 視覚と音声で情報が混在すると読者が混乱
- **専門用語は原稿で短く補足**: 用語自体は本文で維持、原稿で 1〜2 文で噛み砕く
- **「・」中点を原稿で「、」に**: 「設定・材料・参加者」→「設定、材料、参加者」
- **数字括弧 `(2)` `(3)` は文章化**: 「(2) アウトカムは…」→「2 点目のアウトカムは…」
- **「今回の○○節で扱う」など既出口ぶり禁止**: 進行順に沿う
- **振り返り時、今回扱わない概念は削除**: 「今回に関係する前提」のみ残す
- **くどい英語併記を避ける**: 「統合、英語の Synthesis」→ どちらか一方で十分
- **前ページ結びと冒頭重複回避**

### (9) 動詞・助詞の精度
- **不自然な動詞-目的語の組み合わせ**: 「方法を投げかける」「~を訴える」「~の必要性を主張する」など、目的語との相性を確認
- **二重表現**: 「課題として求めた」(「として」+「求めた」の重複)
- **助詞の意味差を意識**: 「~における」(in: 文脈)と「~による」(by: 行為主体)
- **因果 vs 現象の助詞使い分け**: 因果なら「ことで」、共起・慣行を述べているなら「ことが多く」「ケースが多く」
- **逆接「にもかかわらず」で対比明確化**: 「前提と現実のギャップ」を明示。「のに」は子供っぽい
- **能動態と受動態の混在を避け主語を統一**: 同一 bullet 内で態がブレない
- **言い切りに違和感があれば「~に値する」「~の対象」**: 「~は批判」→「~は批判に値する」

### (10) 構造化(階層・bullet・見出し)
- **bullet 末尾の名詞形 / 述語形を統一**: 「〜の難しさ」と「〜が難しい」を同一節で混在させない
- **並列 bullet の見出し名詞句は性質名で揃える**: 「○○の不足」「○○の少なさ」と性質名で並べるなら、形容詞+名詞も性質名化(例: 「能動的な参加者」→「参加者の能動性」)
- **見出しの太字は分割せず全体に**: `**A**(補足)**B**` →`**A(補足)B**`
- **見出しと bullet の意味的重複を避ける**
- **「ラベル: 値」形式の見出しは統合した名詞句に**: 「主なリスク: バイアス(様々な段階で生じうる)」→「**様々な段階で生じうるバイアスのリスク**」
- **ラベルを残す場合は `:` ではなく助詞 `は/を/が` で繋ぐ**: 「**本質**は、~」「**焦点**は、~」
- **指示語「これら」「その」は具体化**: 「これらの制約」→「**1 の制約**」のように番号参照
- **副詞の重ねを避ける**: 「定期的に批判的にまとめる」→「批判的にまとめ、定期的に更新する」
- **論理的齟齬を避ける**: 「考え方は運動」のように主語と述語の概念カテゴリーが不一致な表現は不自然
- **bullet 内の順序**: 一般説明 → 性質 → 例
- **「結論文 + 唐突な列挙導入」を避け繋ぎ文を入れる**
- **bullet 列挙の「結果/結論」は別段落に分離**
- **留意点・注意点は段落より bullet 化 + 理由を sub-bullet で構造化**
- **報告・活用の対象を主語に置き直す**: 「報告すべきは X」→「この判断は、X が報告すべき」
- **階層化で論理関係を示す**: 「根拠となる事実:」「示される事実:」ラベル + sub-bullet
- **オーバーフロー時はサイズ縮小ではなく分割**
- **順序性のある列挙は markdown 番号付きリスト**: 「第一」「第二」より `1.` `2.`
- **小見出しに括弧補足を直接付けない**: 前置きや補足は別 bullet に独立
- **見出し(subtitle)はテーマを端的に**: 組織名・図名だけでなく概念や領域も入れる。硬い名詞句より並列が自然。本文と重複する年数等は不要
- **本文と見出しで文脈補完できる冗長表現は省略**
- **重要な引用句のみの bullet は意味不明**: 日本語訳併記、「発言:」ラベル + 訳
- **「意味するところ」のような要点明示ラベルを使う**
- **次セクションへの繋ぎは本文にも入れる**
- **括弧補足 `(...)` は最小限**
- **「○○として」「(△△から)」のような意味のない括弧は文意に組み込む**

### (11) 和欧混在時のスペース規則(プレーンテキスト出力時)

**背景**: Markdown/LaTeX/HTML では組版エンジンが自動でアキを入れるため、ソースで空けなくてよい(むしろ二重アキになる)。プレーンテキスト(応募フォーム、メール本文、Slack、SNS、フォーム自由記述)ではソースの空白がそのまま可視化される。「日本語と英数字の間に全角/半角スペースを入れる」は AI 生成テキストの典型癖で、ネイティブは詰めるのが自然。

**適用先**: プレーンテキストの日本語(組版エンジンの自動アキが効かない出力先)。**本 skill 呼び出し時にプレーンテキスト出力があれば必ずチェック**。Markdown/LaTeX 内は組版エンジンに任せて基本ノータッチ。

- **日本語と英単語・数字の間のスペースを詰める**
  - ❌ NG: `A 社 の SaaS を 3 年 使用` / `Web は Next.js で 実装`
  - ✅ OK: `A社のSaaSを3年使用` / `WebはNext.jsで実装`
- **英単語同士の間の半角スペースは保持**(元々の英語表記の一部)
  - ✅ OK: `Node.js Express` / `React Native` / `Google Cloud Platform`
- **数字と単位・接続語の間もスペースなし**
  - ❌ NG: `10 ヶ月 / 500 名 / 3 ヶ国`
  - ✅ OK: `10ヶ月 / 500名 / 3ヶ国`
- **括弧の内側と外側**
  - 括弧内が英数字だけ・括弧外が日本語 → 詰める: `TypeScript(3年)` / `Node.js(BE)`
  - 括弧内の英単語同士のスペースは保持: `(Next.js 14)` / `(App Router)`
- **例外**: 引用元や公式表記が空白を含む固有名詞・タイトル・URL(例: 論文タイトル、Twitter 名)は原文尊重

## AI生成典型構文の回避例

| Before | After |

## 数字表記の統一ルール

- 章番号と本文中の年号・序数を同じスタイル(算用 or 漢数字)に揃える
- 作中固有番号(第十九番スイッチ等)・引用(講義第三回等)は原典に従う(統一の例外)

## 修正ワークフロー (反復)

1. **lint**: `python -m ja_prose_lint <file>` で機械的検出。high(主に pos_errors)はノイズ多めだが、`continuous_kanji` `repeated_phrases` は有用
2. **agent レビュー**: 下記 prompt テンプレで agent を起動、観点別に候補を抽出
3. **候補提示**: 高/中/低 優先度 + 維持判断で整理、ユーザ判断を仰ぐ
4. **Edit**: ユーザ選択を Edit で適用
5. **(必要なら) PDF 再生成**: 学術レポート提出時のみ
6. **再度 agent レビュー**: 残存・新規指摘を抽出、ループ
7. 「高」がゼロになるまで繰り返す。「中」「低」はユーザ判断

## 注意点

- **トレードオフ**: 「論理装置(操作的定義/留保強度/問題提起)」と「AI臭の表現」 は同じ表現空間で競合する。両立は構造的に難しいが、命名宣言を本文末に押しのける/留保語を平易動詞句で置換 等で両立可能
- **中庸結語の文脈別判断**: 観点(4) では回避対象だが、観点(7) では引用元外情報・解釈の限界明示として推奨。**書き手の主張は断定、引用元外情報や解釈は中庸表現**で使い分け
- **「本稿は」自己言及の文脈別判断**: 観点(4) では論文での自己言及はメタ的で AI 臭。一方、口頭発表での話題転換シグナル(「原典の内容に戻ります」など、観点(7))は別軸。論文/プレゼンで使い分け
- **往復回避**: agent は新しい指摘を生み出すことがあるが、ユーザの直前判断と方向性が逆になる場合は往復しない
- **論文 vs エッセイ**: 「である」調が標準だが、媒体次第で「です・ます」 や口語混じりもあり。skill は文体を強制しない
- **敬体・常体の混在禁止**: 同一文書(特に原稿・プレゼンノート)で敬体と常体を混在させない
- **専門用語の維持**: 本論の中核概念・固有名詞・直接引用は触らない
- **記号は用法で判断する(文章 vs データ)**: 観点(6) のダッシュ・中黒・機種依存記号の置換は**文章中の用法**が対象。表のセル内で別の役割を担う記号は維持する
  - 表内の `—`(em dash)が「該当なし/データなし」のマーカーなら維持。一律置換すると意味が消える
  - 表セル内の列挙の中黒は、読点より視認性が高いため維持してよい(セルは折り返しが効かず横幅が限られる)
  - 表内の `→` が因果・遷移を示すなら維持(文章化するとセルが冗長になる)
  - 一方、**本文の `+` `×` `→` は観点(6) どおり文章化する**(「A + B」→「A と B」等)
- **組版されない Markdown は既存ファイル群のスタイルに合わせる**: 観点(11) は「Markdown/LaTeX 内は組版エンジンに任せてノータッチ」だが、**組版を経ずそのまま読まれる Markdown**(`~/.claude/docs/` 配下の docs、リポジトリの README 等)は実質プレーンテキスト
  - 判断基準は「組版エンジンを通すか」であって拡張子ではない
  - この場合は**同じディレクトリの既存ファイルの和欧スペース有無を先に確認し、それに揃える**(詰める/空けるのどちらでも、文書群として一貫することが優先)
  - 確認コマンド例: `grep -ohE "[ぁ-んァ-ヶ一-龥][0-9A-Za-z]+" <既存ファイル> | head`

## 自己改善 (skill 自身の更新)

skill を使う中で得た新パターンは、Claude が SKILL.md に追記して育てる。

### 追記の判断基準
- **自動追記OK (ユーザ承認不要、1行告知のみ)**:
  - 明確な単語置換 (例: 還元→単純化)
  - 既知カテゴリの構文パターン追加 (例: 「〜うる」 系の新例)
  - 観点漏れの追記 (既存10観点に収まる範囲)
- **要確認 (ユーザに提案してから追記)**:
  - 既存対応表と矛盾するもの
  - 文脈依存性が強いもの (用途・媒体で逆方向の判断になる)
  - 新カテゴリ (観点) の追加
  - ワークフローの大幅変更

### 追記タイミング
- ユーザが修正を採用した直後
- 「次の指摘どうぞ」 等の応答末尾に「skill 追記: ○○→○○ を対応表に追加した」 と1行告知 (自動追記の場合)
- ユーザの方針指示・反論があれば「注意点」 セクションに学びを記録

### 追記場所マッピング
